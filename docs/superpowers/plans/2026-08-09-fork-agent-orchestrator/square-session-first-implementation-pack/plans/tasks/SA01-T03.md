# SA01-T03 — Windows ConPTY, input/output/resize/cancel, and descendant cleanup

- Phase: SA01 — Windows lifecycle and AO platform hardening
- Gate contribution: A1
- Prerequisite: A0
- May run parallel with: SA01-T05 on a separate branch/worktree
- Scope: Windows runtime/platform leaves and deterministic fixtures only

## 1. Objective

Prove and, where necessary, repair AO's existing Windows process/ConPTY runtime so Square can rely on it instead of rebuilding terminal infrastructure. Cover interactive input, Unicode/ANSI output, resize, quiet work, cancellation, nested descendants, redirected parent handles, cleanup, and bounded resource stability.

The goal is a narrow reusable platform boundary, not another certification framework.

## 2. Required preflight source map

Identify exact source for:

- Windows process runtime selection;
- ConPTY creation/start/resize/input/output/close;
- child process creation flags and standard-handle behavior;
- terminal WebSocket/mux boundaries;
- cancellation/stop/kill;
- process-tree discovery/cleanup;
- runtime/session lifecycle callbacks;
- existing Windows tests/fixtures;
- SafeHandle/native-handle ownership and goroutine/thread ownership;
- current use or absence of Windows Job Objects.

Report whether AO uses ConPTY directly, a library, or another helper, and all relevant dependency versions/licenses.

## 3. Locked requirements

- interactive character-mode CLI behavior is preserved;
- terminal output is captured once by the daemon runtime and forwarded without leaking to parent stdout/stderr;
- input and resize use explicit terminal APIs;
- a quiet process remains active when process/child evidence says it is alive;
- graceful cancellation is attempted before authorized hard stop;
- hard stop cleans the complete descendant tree;
- UI/terminal viewer closure does not own the process;
- no global inheritable handle or process-name kill;
- no model monitors terminal health;
- exact runtime/process identity is recorded;
- terminal escape output cannot invoke host commands.

If existing AO containment does not guarantee descendants on Windows, a narrow Job Object implementation is permitted in the Windows runtime adapter after recording an ADR. Do not move workflow logic into it.

## 7. Process startup contract

Verify through integration tests, not source-string matching:

- child is attached to the intended ConPTY;
- stdout and stderr markers enter the ConPTY stream;
- neither marker leaks to separately redirected parent stdout/stderr;
- working directory/environment/arguments preserve spaces and Unicode;
- handles not intended for child inheritance are non-inheritable;
- process/terminal/container handles have one documented owner and close point;
- output reader starts before the child can overrun or block the channel;
- startup failure releases every acquired resource.

Do not cargo-cult the former .NET proof. Use AO's current Go/runtime design and Windows documentation.

## 8. Stream and terminal behavior

- preserve byte order;
- support UTF-8 and ANSI sequences;
- do not silently truncate required prompt/completion markers;
- high-volume output remains bounded in presentation without blocking process drain;
- read completion/broken pipe is distinguished from unexpected error;
- resize is observed by the hosted fixture;
- input reaches the fixture exactly once;
- terminal close and viewer detach are different operations.

## 9. Cancellation and containment

### Graceful path

1. request checkpoint/interrupt through existing supported mechanism;
2. wait bounded grace period;
3. observe natural exit and descendants;
4. close terminal/runtime resources;
5. report outcome.

### Hard-stop path

Only after explicit test authorization:

1. terminate complete runtime process tree/container;
2. continue draining/closing terminal safely;
3. verify every recorded PID plus creation identity is gone;
4. report hard-stop use separately from natural exit.

Natural scenarios cannot silently pass by invoking cleanup hard stop.

## 10. Resource stability

Avoid arbitrary pass thresholds based on a single run. Required evidence:

- 25 sequential cycles of each core scenario or a justified smaller expensive subset;
- 10 rounds at concurrency 1, 4, and 8 for representative normal/burst/quiet/cancel/nested cases;
- process count and owned-runtime counters return to zero after each session;
- no continuing round-to-round growth in OS handles/goroutines/threads after warmup and bounded quiescence;
- exact peak/stable values recorded;
- no surviving descendants.

A stable one-time runtime plateau may be documented. Linear persistent growth is a failure. Do not raise a threshold to hide it.

## 14. Acceptance criteria

- **SA01-AC-13:** all fixture I/O/resize/exit scenarios pass on Windows.
- **SA01-AC-14:** stdout/stderr enter ConPTY and do not leak to parent streams.
- **SA01-AC-15:** viewer/UI closure does not stop process.
- **SA01-AC-16:** graceful and hard-stop paths are distinct and complete.
- **SA01-AC-17:** no descendant survives authorized hard stop or owner loss scenario tested.
- **SA01-AC-18:** no persistent per-cycle runtime resource growth after warmup/quiescence.
- **SA01-AC-19:** no provider account is required.

## 15. Mandatory STOP conditions

Stop when:

1. target AO terminal architecture cannot support interactive Windows CLIs;
2. correct operation requires globally inheritable handles or unsafe shell-string execution;
3. complete descendant containment cannot be achieved in the runtime leaf;
4. a terminal close thread/goroutine remains blocked;
5. output leaks after correct startup/handle isolation;
6. linear resource growth persists;
7. natural scenarios require cleanup hard stop;
8. repair requires changing Square workflow/domain/UI;
9. a new native dependency has unclear license/security;
10. test evidence would require credentials or valuable repositories.
