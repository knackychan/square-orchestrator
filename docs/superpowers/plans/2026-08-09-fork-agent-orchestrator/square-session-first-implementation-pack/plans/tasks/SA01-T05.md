# SA01-T05 — Worktree cleanup and dirty-state safety

- Phase: SA01 — Windows lifecycle and AO platform hardening
- Gate contribution: A1
- Prerequisite: A0
- May run parallel with: SA01-T03 in separate branch/worktree
- Scope: AO workspace/worktree platform leaves and tests

## 1. Objective

Prove and harden Git worktree creation, ownership, cleanup, and restart behavior on Windows. A successful agent process must not hide cleanup failure, and cleanup/update/uninstall must never delete dirty, untracked, locked, ambiguous, or user-owned work.

## 2. Preflight source map

- dirty/untracked detection;
- branch collision and stale metadata handling;
- error normalization and UI/API status;
- existing Windows tests.

Record SA00 baseline findings relating to Windows cleanup.

## 3. Locked rules

- one active writer binding owns one Square/AO-managed worktree;
- repository root and worktree paths are canonicalized;
- no shell-string Git invocation;
- dirty/untracked work is preserved;
- cleanup warning is distinct from task/process success;
- access-denied/in-use paths are not force-deleted;
- worktree ownership must be proven before removal;
- main repository and user-created worktrees are never treated as managed temp worktrees;
- stale Git metadata is reconciled conservatively;
- restart does not recreate or delete a worktree blindly;
- spaces, Unicode, long paths, and case-insensitive comparison are tested.

## 6. Worktree ownership record

A managed worktree must be associated with:

- project/repository identity;
- AO session/task identity;
- canonical path;
- branch/ref;
- creation baseline commit;
- creation generation/owner;
- created-by-AO marker/fact;
- dirty/untracked status at cleanup;
- cleanup state/reason;
- last error.

A path alone is not sufficient proof of ownership.

## 7. Cleanup state model

At minimum:

```text
ACTIVE
RELEASE_REQUESTED
CLEAN_REMOVABLE
DIRTY_RETAINED
UNTRACKED_RETAINED
IN_USE_RETRYABLE
AMBIGUOUS_OWNERSHIP
GIT_METADATA_STALE
REMOVED
CLEANUP_WARNING
CLEANUP_FAILED
OWNER_ACTION_REQUIRED
```

Process outcome and cleanup outcome are separate fields. A task may be `SUCCEEDED` with `CLEANUP_WARNING`; UI/API must not hide it.

## 8. Safe cleanup algorithm

1. prove managed ownership and canonical repository relation;
2. ensure no current writer/controller binding uses it;
3. inspect Git worktree metadata;
4. inspect tracked modifications, staged changes, untracked files, conflicts;
5. inspect active process handles where feasible through existing runtime ownership;
6. remove only clean, owned worktree through Git-aware operation;
7. do not use recursive filesystem deletion as normal path;
8. on failure retain path/branch/metadata and expose action;
9. prune only proven stale metadata and never user work;
10. record every cleanup attempt idempotently.

## 9. Required fixture matrix

Use disposable repositories:

- clean worktree create/remove;
- path with spaces;
- Unicode repository/worktree/file;
- uncommitted tracked change;
- staged change;
- untracked file/directory;
- merge conflict;
- open file/process lock;
- current working directory held by child process;
- long path within supported policy;
- branch-name collision;
- existing user-created worktree;
- stale `.git/worktrees` metadata;
- missing directory but present metadata;
- directory exists but ownership record missing;
- process succeeds but cleanup fails;
- cancellation/hard stop then cleanup;
- daemon restart during cleanup;
- repeated cleanup request.

## 10. Windows/process coordination

Worktree cleanup must use the runtime/session facts from SA01-T03/T04 when available. Do not guess that a process is gone from terminal status alone. Where T04 is not yet accepted, record deferred integration and use deterministic fixture ownership.

## 13. Acceptance criteria

- **SA01-AC-26:** every owned clean fixture can be created and removed safely.
- **SA01-AC-27:** dirty/untracked/conflicted/user-owned work is retained.
- **SA01-AC-28:** cleanup failure is separate from process/task result.
- **SA01-AC-29:** spaces/Unicode/branch collision/restart cases are safe.
- **SA01-AC-30:** repeated cleanup is idempotent.
- **SA01-AC-31:** no path outside proven managed worktree is deleted.

## 14. Mandatory STOP conditions

Stop when:

1. current code can delete unproven/user work and a narrow safe fix is unclear;
2. safe ownership requires a schema migration overlapping SA03 rather than an AO platform fact;
3. Git commands require shell-string execution;
4. Windows locks can only be bypassed with force deletion;
5. main repository or user-created worktree is removed/damaged in a test;
6. test fixture path escapes its temporary root;
7. cleanup depends on killing ambiguous processes;
8. upstream source structure requires broad redesign;
9. new dependency license/security is unreviewed;
10. evidence contains real repository data.
