# SA00-T05 — Adoption gate A0

- Phase: SA00 — Fork adoption and reproducible baseline
- Type: owner/reviewer gate; no implementation authority
- Prerequisites: accepted SA00-T01, SA00-T02, SA00-T03, SA00-T04 receipts
- Output: `PASS`, `CONDITIONAL_PASS`, or `BLOCKED`

## 1. Objective

Independently review whether the downstream fork is legally, technically, and procedurally safe to enter Windows platform hardening. Confirm exact upstream identity, unchanged baseline evidence, attribution, downstream identity isolation, telemetry/updater defaults, owner-approved authority, and a clean source boundary.

A0 does not approve Square workflows, migrations, UI, or release behavior. It only accepts the fork as a controlled starting point.

## 2. Reviewer independence

The reviewer must not rely only on task completion reports. Review raw Git refs, diffs, command logs, manifests, and source changes. When the same agent performed SA00 tasks, use a fresh review context or human review.

## 4. Review questions

### Source identity

- Does `v0.12.1^{commit}` equal `square-base-v0.12.1^{commit}`?
- Does the target begin with `1df40e9`?
- Is `upstream` preserved?
- Is `square/main` a descendant of the baseline without history rewrite?
- Has any upstream tracked source changed before the adoption changes were committed?

### Baseline

- Were all documented build/test/package commands run or honestly classified?
- Are failures pre-existing and reproducible?
- Did SA00-T02 avoid repairing or hiding them?
- Are baseline omissions acceptable for entering SA01, or do they make later evidence unreliable?
- Are toolchain versions compatible with pinned source?

### Legal and product identity

- Is Apache-2.0 and applicable attribution preserved?
- Are modified-file and third-party notice responsibilities recorded?
- Do Square development builds avoid official AO telemetry/update behavior?
- Are Square and AO data/config/runtime/worktree identities separated enough for SA01 tests?
- Are final identity/signing/installer decisions clearly parked rather than accidentally frozen?

### Authority

- Did the owner explicitly accept the session-first architecture amendment?
- Do authority hashes verify?
- Is the rounded session-first reference the approved UI direction?
- Are the previous .NET and global-dashboard plans marked research/superseded rather than silently active?
- Are model-routing and Task Manager boundaries explicit?

### Repository hygiene

- Are product/dependency/generated files free of unrelated drift?
- Are evidence files privacy-safe?
- Are all manifests valid?
- Is the working tree clean at review?
- Has no push/update/publish occurred unexpectedly?

## 5. Decision meanings

### PASS

All A0 acceptance criteria are met. SA01 tasks may be dispatched according to prerequisites.

### CONDITIONAL_PASS

Only a bounded, non-critical documentation/environment item remains. The condition must:

- not weaken source identity, license, data isolation, telemetry/updater safety, or owner authority;
- have a named owner/task/deadline;
- not be hidden from downstream packets.

A conditional pass cannot waive an unknown source commit, dirty baseline, unreviewed license, official updater risk, telemetry transmission, or ambiguous authority.

### BLOCKED

Any critical input is missing, contradictory, unverifiable, unsafe, or polluted by unclassified source changes. No SA01 implementation begins except a narrowly approved gate-fix task.

## 7. Gate criteria

- **A0-01:** exact upstream tag/commit/baseline tag verified.
- **A0-02:** downstream Git/remotes/branch history controlled.
- **A0-03:** unchanged Windows baseline complete enough and failures classified.
- **A0-04:** no hidden product/dependency drift.
- **A0-05:** Apache/attribution inventory accepted.
- **A0-06:** telemetry disabled by default in Square builds.
- **A0-07:** official AO updater cannot replace a Square build.
- **A0-08:** Square/AO development data and runtime identities are separated.
- **A0-09:** session-first architecture amendment explicitly owner accepted.
- **A0-10:** authority files/hash/index verify.
- **A0-11:** previous implementation paths are accurately superseded/preserved.
- **A0-12:** evidence/receipts are complete and privacy-safe.

All criteria must be `PASS` for an unconditional gate pass.

## 8. Verification commands

Run raw checks rather than copying receipt values:

```powershell
git rev-parse HEAD
git rev-parse "v0.12.1^{commit}"
git rev-parse "square-base-v0.12.1^{commit}"
git remote -v
git status --short
git log --graph --decorate --oneline --max-count 20
git diff --stat "square-base-v0.12.1"..HEAD
git diff --name-status "square-base-v0.12.1"..HEAD
```

Recompute:

- every SA00 evidence manifest;
- authority manifest;
- receipt hashes;
- source/package lock hashes referenced by baseline evidence.

Run targeted tests proving current telemetry/updater/data defaults rather than trusting old logs.

## 9. Forbidden actions

The gate reviewer does not:

- edit code to make the gate pass;
- relabel a failed command as passed;
- delete evidence;
- alter previous receipts;
- accept an unverifiable commit/tag;
- dispatch SA01 before writing the gate result;
- approve later product architecture beyond A0 scope.

A correction requires a new explicit `SA00-FIXxx` task, then a superseding gate review.
