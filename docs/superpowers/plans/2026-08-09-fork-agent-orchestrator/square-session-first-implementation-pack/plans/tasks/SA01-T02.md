# SA01-T02 — Single daemon and Square data-directory ownership

- Phase: SA01 — Windows lifecycle and AO platform hardening
- Gate contribution: A1
- Prerequisites: A0 and accepted SA01-T01
- Scope: local daemon identity, endpoint ownership, and data-root isolation

## 1. Objective

Guarantee that one compatible per-user Square daemon owns one Square data directory/database and local endpoint. Simultaneous desktop/CLI launches must converge on that daemon. Stale run files, unrelated listeners, official AO, incompatible versions, or ambiguous process identity must never trigger unsafe reuse or blind duplicate spawn.

## 2. Required preflight

Map exact source paths/symbols for:

- current default data/config/log/cache/worktree roots;
- database open and migration startup;
- port selection/listen address;
- run/PID/port/lock file writing and reading;
- daemon instance/version/status response;
- frontend and CLI daemon discovery/spawn;
- shutdown and stale-file cleanup;
- tests for multiple starts.

Review SA00-T03 identity register and SA01-T01 lifecycle changes.

## 3. Locked contract

A daemon endpoint is reusable only when all required values match:

```text
product identity = Square
protocol/API compatibility = accepted range
per-user ownership = current user context
expected data-root identity = exact canonical root
instance readiness = ready
instance generation/ID = valid
```

PID alone is insufficient proof. A port responding with unrelated HTTP is not a Square daemon. A stale file is not authority.

Official AO and Square may coexist. They must not share:

- database/data root;
- run/PID/port file;
- endpoint identity;
- worktree root;
- updater/telemetry identity.

## 6. Required implementation

### Product/data identity

Resolve canonical Square roots through one typed configuration object. Support explicit test overrides. Canonicalize Windows paths before comparison.

### Instance identity

At daemon startup create a cryptographically unpredictable instance ID and generation record. Expose it with:

- product ID;
- daemon version;
- protocol/API version;
- canonical data-root fingerprint or non-sensitive ID;
- started-at timestamp;
- process identity where available;
- readiness state.

Do not expose secrets or full user paths unnecessarily to remote/untrusted surfaces; local diagnostic output may include redacted/canonical paths by policy.

### Single ownership

Use existing safe primitives where possible. The algorithm must prevent two writers even when UI/CLI start concurrently:

1. acquire per-user/per-data-root startup ownership atomically;
2. if ownership exists, verify compatible live endpoint;
3. connect to the verified owner;
4. if stale, prove staleness before cleanup;
5. only one contender may create/listen/open/migrate the database;
6. publish readiness atomically after DB and API are ready;
7. release/replace stale records only under owned startup lock.

A file lock, named mutex, exclusive-create/run record, endpoint handshake, or combination may be used if it works on Windows and requires no unreviewed dependency. Record the decision in ADR.

### Endpoint

- loopback only;
- collision with unrelated listener produces typed error or safe alternate endpoint under the same ownership record;
- clients never scan arbitrary ports and trust the first response;
- run record is atomically written and permissioned as narrowly as current platform allows;
- port/instance/product/protocol/data-root values are validated together.

### Database ownership

- one daemon opens authoritative DB for writes;
- clients never open it;
- simultaneous starts cannot run migrations concurrently;
- a daemon pointed at another Square data root is a separate explicitly configured instance, not silently reused;
- official AO DB is never opened due to fallback.

## 7. Stale-state classification

Classify:

- `NO_RECORD`
- `STARTING_OWNER`
- `READY_COMPATIBLE`
- `READY_INCOMPATIBLE`
- `STALE_RECORD_NO_PROCESS`
- `STALE_RECORD_PROCESS_ID_REUSED_OR_AMBIGUOUS`
- `UNRELATED_LISTENER`
- `DATA_ROOT_MISMATCH`
- `OWNERSHIP_CONFLICT`

Ambiguous process identity must not be killed. Surface recovery instructions or owner-gated cleanup.

## 8. Required tests

### Deterministic/unit

- path canonicalization, spaces, Unicode, case-insensitivity;
- data-root fingerprint/identity;
- run-record encode/decode/version/atomic replacement;
- handshake compatibility matrix;
- stale classification;
- unrelated HTTP listener;
- product/data mismatch;
- corrupt/partial record;
- no secret leakage.

### Windows concurrency

- 2, 8, and 20 simultaneous CLI/UI start attempts;
- exactly one daemon/database owner;
- all successful clients resolve same instance ID;
- no duplicate migration/open;
- losing contender exits/connects cleanly;
- stale record after crash reconciles;
- PID reuse/ambiguous identity does not kill process;
- official AO and Square run simultaneously without shared files/endpoint/DB;
- two explicit Square test data roots remain isolated.

### Restart

- normal stop removes or marks run record safely;
- crash leaves recoverable stale state;
- restart publishes a new instance generation;
- client reconnect notices generation change;
- active-session recovery is SA01-T04, not silently relaunched here.

## 10. Acceptance criteria

- **SA01-AC-07:** concurrent starts create one compatible daemon and DB writer.
- **SA01-AC-08:** all clients verify the same instance/product/protocol/data identity.
- **SA01-AC-09:** stale/ambiguous/unrelated states fail safely.
- **SA01-AC-10:** official AO and Square coexist without data/runtime collision.
- **SA01-AC-11:** only daemon opens authoritative Square DB.
- **SA01-AC-12:** no new schema/product feature is introduced.

## 11. Mandatory STOP conditions

Stop when:

1. one-owner enforcement needs a system service/elevation not approved;
2. exact user/data-root ownership cannot be determined safely;
3. preventing duplicate writers requires changing SQLite schema/migrations in this task;
4. stale cleanup requires killing an ambiguous process;
5. official AO cannot coexist without broad final rebrand work;
6. a new external dependency is required;
7. API compatibility cannot be verified before reuse;
8. tests expose real user database/data;
9. concurrent starts still migrate/open the DB twice;
10. source scope overlaps SA01-T03/T04 materially.
